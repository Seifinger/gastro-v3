# Decisions

## 2026-09-23 — Architecture baseline
- Node 22 ESM, framework-free browser code; Express for servers only. Generated sites are static.
- AJV Draft-07 and ajv-formats validate source values without inventing confirmed facts.
- Optional fields use `{ value, status }`; absent fields become `{ value: null, status: 'draft' }` without modifying input.
- Supplemental optional schema fields `video`, `speisekarte`, `testimonials`, and `historie` enable the requested rule-based section selection; they obey the same provenance contract.
- A photo collection cannot be confirmed while containing unconfirmed images; empty values cannot be confirmed. A user may still explicitly mark a non-empty value confirmed, because the briefing itself is the provenance source.
- Public repo contains no secrets or customer data; generated docs content and runtime files are ignored. Public publishing must use reviewed, confirmed facts and a separate deliberate deployment step.
- Scripts start only after dependencies are installed; no build framework, CSS framework, icon library, or build-time AI call.

## 2026-09-23 — v1 data source finding
- `Seifinger/gastro-webagentur` has no `data/betriebe.json` and no committed database of confirmed restaurant facts. Real per-restaurant data in v1 is either (a) fetched live from the Google Places API at runtime (not stored in the repo), or (b) the four fictional pilot briefings under `v2/briefings/*.json` (each explicitly marked `"fiktiv": true`), which use a different nested `{ wert, status, quelle }` shape per section (`betrieb`, `konzept`, `karte`, `medien`, ...) with statuses `uebernommen` (taken from Google Places — i.e. confirmed) / `vorschlag` (agency suggestion, e.g. stock menu/photos) / `unbekannt` (unknown).
- `scripts/migrate-from-v1.js` therefore treats `<v1 repo>/v2/briefings/*.json` as the actual migratable data source, maps `uebernommen` → `confirmed`, `vorschlag`/`unbekannt` → `draft`/`unknown`, and never invents `betriebe.json`. If the v1 repo path or its `v2/briefings` directory is missing, it fails with a clear, actionable error instead of fabricating output. It reads only from the v1 path and writes only under `data/migrated/` in this repo.

## 2026-09-23 — Section B: 20 blueprints
- Contract: every blueprint's `index.js` exports `render(briefing, tokens, ctx)` returning `{ html, css, altText? }`, plus re-exports `css` and `motion` from its own `style.js`/`motion.js` for introspection (used later by the judge). `ctx` optionally carries `cta` (label/href for the blueprint's own call-to-action) and `apiBase` (the wirt-portal origin used by `reservation-form`/`order-embed` to build their POST endpoints as `${apiBase}/betrieb/${slug}/...`).
- `src/blueprints/_shared/util.js` holds only escaping and the provenance gate (`confirmed()`/`confirmedPhotos()`) — not a shared template. Every blueprint still builds its own distinct HTML structure and CSS; nothing is a renamed copy of another.
- Asymmetry is real, not cosmetic: `gallery-mosaic` uses an irregular CSS grid (large/small cells via `nth-child` spans), `menu-cards` uses a 6-column dense grid with varying spans (not three equal tiles), `hero-editorial`/`hero-split` use unequal column ratios, `testimonial-grid` uses CSS columns (masonry-like) instead of a uniform grid.
- `reservation-form` and `order-embed` are functionally real, not decorative: both do client-side `fetch()` POSTs with inline vanilla JS (no framework), server-authoritative validation is expected on the wirt-portal side (Section F), and `order-embed` fetches the current no-show configuration and consent text from `${apiBase}/betrieb/:slug/konfiguration` at load time so the legally relevant consent text is never duplicated/hardcoded on the static page.
- Only `confirmed` status data is ever interpolated into markup (`confirmed()`/`confirmedPhotos()` in `_shared/util.js`); a blueprint whose required confirmed field is missing renders an empty string so the composer can skip it rather than showing a fabricated placeholder photo/price/quote.
- `tel-CTA` (mentioned in the brief for `hauptaktion: anrufen`) is not one of the 20 named blueprints; it is a one-line `tel:` call-to-action assembled directly by the composer/renderer (Section C/D), since it has no independent layout to speak of.

## 2026-09-23 — Section C: Composer
- `src/composer/index.js` is a pure, deterministic rule engine: `compose(briefing)` derives tokens, then independently picks a hero, an optional story section, 0-2 product sections, an optional gallery, an optional social-proof section, and the mandatory conversion element for `hauptaktion` (`reservieren`→`reservation-form`, `bestellen`→`order-embed` only if a confirmed menu exists, `anrufen`→`tel-cta` only if a confirmed phone number exists, `informieren`→none). Sections are pushed in that fixed dramaturgical order (Hook → Vertrauen → Produkt → Beweis(Ambiente+Social Proof) → Aktion).
- Any variety among equally valid choices (e.g. `hero-split` vs `hero-fullbleed` vs `hero-editorial` when ≥2 confirmed photos exist, or which of `menu-cards`/`menu-board`/`menu-list` for ≥3 menu items) is picked via `seedHash(briefing.id) % options.length` — a stable djb2-style hash, never `Math.random()`. The same briefing always composes to the same sections.
- `ensureAsymmetry()` guarantees at least one asymmetric desktop section by swapping in an asymmetric sibling blueprint (`menu-list/menu-board`→`menu-cards`, `gallery-single/strip`→`gallery-mosaic`, `testimonial-solo`→`testimonial-grid` when ≥2 quotes, or the hero to `hero-split`/`hero-editorial`) before falling through — this only ever swaps between blueprints whose required confirmed data is already present, never fabricates data to unlock one.
- `ensureSignatureMoment()` flags exactly one section `ctx.signature = true`, preferring the first `signatureCapable` blueprint in dramaturgical order (usually `dish-hero`, else the hero itself).
- When fewer than 6 sections can be built from confirmed content, or the mandatory conversion action can't be rendered (missing confirmed phone/menu), `compose()` returns `buildStatus: 'insufficient'` with human-readable `reasons` instead of forcing placeholder sections to hit the 6-9 range — the dashboard (Section E) surfaces this status directly rather than letting such a site publish.
- Tests (`test/composer.test.js`) cover five briefings across all four `hauptaktion` values, verifying build-readiness, exactly-one signature moment, deterministic re-composition, forced asymmetry, dramaturgical ordering, and the explicit-insufficiency path for missing confirmed contact data.

## 2026-09-23 — Section D: Renderer, Judge, build/publish
- Added an optional `freigabe` field (`{status, value: boolean}`) to the briefing schema — a deviation from the initially committed schema, needed because publishing must gate on an explicit agency approval, which didn't exist yet. Undefined/draft `freigabe` behaves exactly like any other optional field (defaults to `{value: null, status: 'draft'}`); only `{status:'confirmed', value:true}` counts as approved for publishing.
- `src/renderer/index.js` concatenates each composed section's own scoped CSS plus a small reset/`prefers-reduced-motion` safety net into one inline `<style>`, builds the Google Fonts `<link>` (only the ≤2 families the site's archetype actually uses, `display=swap`, with `preconnect` to both `fonts.googleapis.com` and `fonts.gstatic.com`), OG/Twitter tags, and a `LocalBusiness`/`Restaurant` JSON-LD block built exclusively from `confirmed` fields (`src/renderer/jsonld.js`). The document opens with an HTML comment recording the engine version (from `package.json`) and archetype.
- `src/judge/index.js` is a hard gate, not advisory: `build.js` refuses to write a site whose judge result has any `level:'error'` finding. It independently re-derives contrast (both body-text AA and CTA 7:1) from the tokens actually used, scans the rendered CSS for forbidden multi-hue decorative gradients (distinguishing them from the neutral black-overlay gradients hero blueprints use for text legibility), rejects the literal `repeat(3,1fr)` three-equal-tiles pattern and generic icon-font class names, enforces an absolute 12px font floor, checks that every asymmetric section actually defines a `@media(min-width:768px)` desktop layout (the "reproducible viewport comparison" — a static, deterministic check of the generated CSS rather than a live-browser screenshot diff, since no extra headless-browser dependency was justified for that alone — see below), and re-verifies exactly one signature moment and at least one asymmetric section rather than trusting the composer's own bookkeeping.
- `scripts/build.js` exports `buildAll({ dataDir, docsDir, publicBaseUrl, filter })` so it's independently testable (`test/build.integration.test.js`) and used by both the CLI entrypoint and `publish.js`. It processes every `data/*.json` briefing independently; a parse/validation/judge failure for one briefing never blocks the others, and no output file is ever written for a failing briefing.
- **The docs/-is-gitignored-but-must-appear-on-Pages contradiction**: resolved by keeping `docs/` gitignored on the working branch (so private briefing data, drafts and any build artifact never land in the browsable history) and adding `scripts/publish.js`, which builds only briefings with a confirmed `freigabe: true`, re-verifies each still passes the judge, and copies *only the resulting static HTML* (no briefing JSON, no secrets) into a dedicated `gh-pages` branch via a temporary `git worktree`. It defaults to a dry run (prints what would publish) and only commits+pushes with an explicit `--push` flag or `PUBLISH_PUSH=1`, since pushing to a public, shared branch is not something to do silently as a side effect of running the build.
- I did not execute `npm run publish --push` during this session — no briefing in this repository currently has a confirmed `freigabe`, and pushing to a public `gh-pages` branch is a repo-wide action outside what was asked. The script's dry-run path and its unit-level logic (via `buildAll`'s `filter`) are covered by tests; the actual git worktree/push path is deliberately not covered by an automated test, since exercising it would require pushing to a real remote.

## 2026-09-23 — Section F: Wirt-portal and notifications
- `src/wirt/store.js` is a straight adaptation of the proven per-betrieb JSON-file design from v1's `betriebStore.js` (table capacity math, overlap detection, no-show bookkeeping), rewritten for v3's file layout and extended with order status `zubereitung`/`bereit` (the brief's "Neu → Zubereitung → Bereit" pipeline) and a per-phone-number `zuverlaessigkeit` (reliability) counter. Every function takes an explicit `slug` and touches only that betrieb's JSON file under `data/runtime/wirt/` (gitignored) — this is the actual tenant-separation mechanism, not just a route-level check. Writes are tmp-file-then-rename for basic write safety.
- Auth (`src/wirt/auth.js`): betrieb-specific login via `scrypt` password hashes (node:crypto, no external auth dependency) stored in `data/runtime/wirt-credentials.json`. Sessions are HMAC-signed, expiring tokens carried in an `HttpOnly` cookie (`WIRT_SESSION_SECRET` env, required — the server refuses to sign sessions without it rather than falling back to a default secret). CSRF is a double-submit cookie: `wirt_csrf` is readable by page JS and must be echoed as `X-CSRF-Token` on every state-changing authenticated request; the server rejects any POST/PUT/PATCH/DELETE where the header doesn't match the cookie. `test/wirt.test.js` verifies both the CSRF rejection and the tenant-isolation guarantee (two betriebe, each only ever sees its own reservations) end-to-end against a real running Express instance.
- There is currently no self-service signup: a betrieb's password is set via `setzeBetriebPasswort(slug, password)`, intended to be called from the agency dashboard (Section E) when a site goes live. Wiring that dashboard button is listed as a remaining gap in the final report — the function and its storage exist and are tested, the dashboard UI trigger for it is not yet built.
- Public, cross-origin routes (`/betrieb/:slug/konfiguration`, `/betrieb/:slug/reservierung`, `/betrieb/:slug/bestellung`) are what the static customer sites' `reservation-form`/`order-embed` blueprints call — `ctx.apiBase` is now threaded from `WIRT_API_BASE_URL` through `renderSite()`/`buildAll()` so built sites point at the actual portal origin instead of a relative path that would only work if both were on the same domain.
- No-show flow matches the brief: the order endpoint requires explicit `noShowZustimmung: true` whenever `noShowSchutzAktiv` is on, and the exact consent text + timestamp are generated server-side and stored on the order (never trusted from the client) — mirroring the v1 design's reasoning that the legal text and the enforced condition must never be able to drift apart. `bestaetigeNoShow` only allows the confirmed amount to be corrected downward, never above what the guest agreed to. `zuverlaessigkeitsWarnung()` surfaces a per-phone-number warning once the configurable threshold is hit, but nothing auto-blocks a guest — the brief is explicit that this is a warning signal, not an automatic block. `src/wirt/pdf.js` renders a Vorgangsquittung (protocol) PDF via the already-present `pdfkit` dependency, explicitly labelled as not an invoice or standalone legal demand.
- Web Push is the default channel (`src/wirt/push.js`, using the `web-push` package added this session), driven by `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`; without those env vars, `sendPushToBetrieb` is a documented no-op rather than throwing, so the portal keeps working with zero push configuration. Telegram (`src/wirt/telegram.js`) is the optional fallback: `sendTelegramMessage`/`notifyBetrieb` no-op without `TELEGRAM_BOT_TOKEN`, and `handleCommand` checks the incoming chat id against the betrieb's own stored `telegramChatId` before running `/bestätigen`, `/absagen`, `/bereit` or `/heute` — one betrieb's Telegram chat can never act on another's data. `startTelegramPolling` is a simple `getUpdates` long-poll loop (no separate public webhook endpoint needed); it is not started by default and not covered by an automated test, since that would require a live Telegram bot token and network access this session doesn't have reason to exercise.
- Frontend is a framework-free PWA: `src/wirt/public/{login,index}.html` + `app.js` (vanilla fetch/EventSource, CSRF token read from the non-HttpOnly cookie) + `manifest.json` + `service-worker.js` (push → `showNotification`). Live updates (new reservation/order, status changes) are pushed to open portal tabs over Server-Sent Events (`GET /api/events`), scoped per-slug via an in-memory `Map<slug, Set<res>>` that is never persisted and never shared across tenants.
- Not yet built in this session, called out explicitly rather than claimed done: the dashboard-side "set wirt password" trigger for a go-live betrieb; a full visual design pass on the portal UI (it is functional/accessible — focus rings, labelled inputs, keyboard-operable buttons — but not art-directed the way customer sites are, since the brief's aesthetic requirement was for the dashboard, not this portal); and any live verification of the Telegram bot loop or Web Push delivery against a real browser/device, since both need external credentials this environment doesn't have.
