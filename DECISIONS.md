# Decisions

## 2026-09-23 — Architecture baseline
- Node 22 ESM, framework-free browser code; Express for servers only. Generated sites are static.
- AJV Draft-07 and ajv-formats validate source values without inventing confirmed facts.
- Optional fields use `{ value, status }`; absent fields become `{ value: null, status: 'draft' }` without modifying input.
- Supplemental optional schema fields `video`, `speisekarte`, `testimonials`, and `historie` enable the requested rule-based section selection; they obey the same provenance contract.
- A photo collection cannot be confirmed while containing unconfirmed images; empty values cannot be confirmed. A user may still explicitly mark a non-empty value confirmed, because the briefing itself is the provenance source.
- Public repo contains no secrets or customer data; generated docs content and runtime files are ignored. Public publishing must use reviewed, confirmed facts and a separate deliberate deployment step.
- Scripts start only after dependencies are installed; no build framework, CSS framework, icon library, or build-time AI call.

## 2026-09-23 — Section B: 20 blueprints
- Contract: every blueprint's `index.js` exports `render(briefing, tokens, ctx)` returning `{ html, css, altText? }`, plus re-exports `css` and `motion` from its own `style.js`/`motion.js` for introspection (used later by the judge). `ctx` optionally carries `cta` (label/href for the blueprint's own call-to-action) and `apiBase` (the wirt-portal origin used by `reservation-form`/`order-embed` to build their POST endpoints as `${apiBase}/betrieb/${slug}/...`).
- `src/blueprints/_shared/util.js` holds only escaping and the provenance gate (`confirmed()`/`confirmedPhotos()`) — not a shared template. Every blueprint still builds its own distinct HTML structure and CSS; nothing is a renamed copy of another.
- Asymmetry is real, not cosmetic: `gallery-mosaic` uses an irregular CSS grid (large/small cells via `nth-child` spans), `menu-cards` uses a 6-column dense grid with varying spans (not three equal tiles), `hero-editorial`/`hero-split` use unequal column ratios, `testimonial-grid` uses CSS columns (masonry-like) instead of a uniform grid.
- `reservation-form` and `order-embed` are functionally real, not decorative: both do client-side `fetch()` POSTs with inline vanilla JS (no framework), server-authoritative validation is expected on the wirt-portal side (Section F), and `order-embed` fetches the current no-show configuration and consent text from `${apiBase}/betrieb/:slug/konfiguration` at load time so the legally relevant consent text is never duplicated/hardcoded on the static page.
- Only `confirmed` status data is ever interpolated into markup (`confirmed()`/`confirmedPhotos()` in `_shared/util.js`); a blueprint whose required confirmed field is missing renders an empty string so the composer can skip it rather than showing a fabricated placeholder photo/price/quote.
- `tel-CTA` (mentioned in the brief for `hauptaktion: anrufen`) is not one of the 20 named blueprints; it is a one-line `tel:` call-to-action assembled directly by the composer/renderer (Section C/D), since it has no independent layout to speak of.

## 2026-09-23 — Section C: Composer
- `src/composer/index.js` is a pure, deterministic rule engine: `compose(briefing)` derives tokens, then independently picks a hero, an optional story section, 0-2 product sections, an optional gallery, an optional social-proof section, and the mandatory conversion element for `hauptaktion` (`reservieren`→`reservation-form`, `bestellen`→`order-embed` only if a confirmed menu exists, `anrufen`→`tel-cta` only if a confirmed phone number exists, `informieren`→none). Sections are pushed in that fixed dramaturgical order (Hook → Vertrauen → Produkt → Beweis(Ambiente+Social Proof) → Aktion).
- Any variety among equally valid choices (e.g. `hero-split` vs `hero-fullbleed` vs `hero-editorial` when ≥2 confirmed photos exist, or which of `menu-cards`/`menu-board`/`menu-list` for ≥3 menu items) is picked via `seedHash(briefing.id) % options.length` — a stable djb2-style hash, never `Math.random()`. The same briefing always composes to the same sections.
- `ensureAsymmetry()` guarantees at least one asymmetric desktop section by swapping in an asymmetric sibling blueprint (`menu-list/menu-board`→`menu-cards`, `gallery-single/strip`→`gallery-mosaic`, `testimonial-solo`→`testimonial-grid` when ≥2 quotes, or the hero to `hero-split`/`hero-editorial`) before falling through — this only ever swaps between blueprints whose required confirmed data is already present, never fabricates data to unlock one.
- `ensureSignatureMoment()` flags exactly one section `ctx.signature = true`, preferring the first `signatureCapable` blueprint in dramaturgical order (usually `dish-hero`, else the hero itself).
- When fewer than 6 sections can be built from confirmed content, or the mandatory conversion action can't be rendered (missing confirmed phone/menu), `compose()` returns `buildStatus: 'insufficient'` with human-readable `reasons` instead of forcing placeholder sections to hit the 6-9 range — the dashboard (Section E) surfaces this status directly rather than letting such a site publish.
- Tests (`test/composer.test.js`) cover five briefings across all four `hauptaktion` values, verifying build-readiness, exactly-one signature moment, deterministic re-composition, forced asymmetry, dramaturgical ordering, and the explicit-insufficiency path for missing confirmed contact data.

## 2026-09-23 — Section D: Renderer, Judge, build/publish
- Added an optional `freigabe` field (`{status, value: boolean}`) to the briefing schema — a deviation from the initially committed schema, needed because publishing must gate on an explicit agency approval, which didn't exist yet. Undefined/draft `freigabe` behaves exactly like any other optional field (defaults to `{value: null, status: 'draft'}`); only `{status:'confirmed', value:true}` counts as approved for publishing.
- `src/renderer/index.js` concatenates each composed section's own scoped CSS plus a small reset/`prefers-reduced-motion` safety net into one inline `<style>`, builds the Google Fonts `<link>` (only the ≤2 families the site's archetype actually uses, `display=swap`, with `preconnect` to both `fonts.googleapis.com` and `fonts.gstatic.com`), OG/Twitter tags, and a `LocalBusiness`/`Restaurant` JSON-LD block built exclusively from `confirmed` fields (`src/renderer/jsonld.js`). The document opens with an HTML comment recording the engine version (from `package.json`) and archetype.
- `src/judge/index.js` is a hard gate, not advisory: `build.js` refuses to write a site whose judge result has any `level:'error'` finding. It independently re-derives contrast (both body-text AA and CTA 7:1) from the tokens actually used, scans the rendered CSS for forbidden multi-hue decorative gradients (distinguishing them from the neutral black-overlay gradients hero blueprints use for text legibility), rejects the literal `repeat(3,1fr)` three-equal-tiles pattern and generic icon-font class names, enforces an absolute 12px font floor, checks that every asymmetric section actually defines a `@media(min-width:768px)` desktop layout (the "reproducible viewport comparison" — a static, deterministic check of the generated CSS rather than a live-browser screenshot diff, since no extra headless-browser dependency was justified for that alone — see below), and re-verifies exactly one signature moment and at least one asymmetric section rather than trusting the composer's own bookkeeping.
- `scripts/build.js` exports `buildAll({ dataDir, docsDir, publicBaseUrl, filter })` so it's independently testable (`test/build.integration.test.js`) and used by both the CLI entrypoint and `publish.js`. It processes every `data/*.json` briefing independently; a parse/validation/judge failure for one briefing never blocks the others, and no output file is ever written for a failing briefing.
- **The docs/-is-gitignored-but-must-appear-on-Pages contradiction**: resolved by keeping `docs/` gitignored on the working branch (so private briefing data, drafts and any build artifact never land in the browsable history) and adding `scripts/publish.js`, which builds only briefings with a confirmed `freigabe: true`, re-verifies each still passes the judge, and copies *only the resulting static HTML* (no briefing JSON, no secrets) into a dedicated `gh-pages` branch via a temporary `git worktree`. It defaults to a dry run (prints what would publish) and only commits+pushes with an explicit `--push` flag or `PUBLISH_PUSH=1`, since pushing to a public, shared branch is not something to do silently as a side effect of running the build.
- I did not execute `npm run publish --push` during this session — no briefing in this repository currently has a confirmed `freigabe`, and pushing to a public `gh-pages` branch is a repo-wide action outside what was asked. The script's dry-run path and its unit-level logic (via `buildAll`'s `filter`) are covered by tests; the actual git worktree/push path is deliberately not covered by an automated test, since exercising it would require pushing to a real remote.

## 2026-09-23 — Section F: Wirt-portal and notifications
- `src/wirt/store.js` is a straight adaptation of the proven per-betrieb JSON-file design from v1's `betriebStore.js` (table capacity math, overlap detection, no-show bookkeeping), rewritten for v3's file layout and extended with order status `zubereitung`/`bereit` (the brief's "Neu → Zubereitung → Bereit" pipeline) and a per-phone-number `zuverlaessigkeit` (reliability) counter. Every function takes an explicit `slug` and touches only that betrieb's JSON file under `data/runtime/wirt/` (gitignored) — this is the actual tenant-separation mechanism, not just a route-level check. Writes are tmp-file-then-rename for basic write safety.
- Auth (`src/wirt/auth.js`): betrieb-specific login via `scrypt` password hashes (node:crypto, no external auth dependency) stored in `data/runtime/wirt-credentials.json`. Sessions are HMAC-signed, expiring tokens carried in an `HttpOnly` cookie (`WIRT_SESSION_SECRET` env, required — the server refuses to sign sessions without it rather than falling back to a default secret). CSRF is a double-submit cookie: `wirt_csrf` is readable by page JS and must be echoed as `X-CSRF-Token` on every state-changing authenticated request; the server rejects any POST/PUT/PATCH/DELETE where the header doesn't match the cookie. `test/wirt.test.js` verifies both the CSRF rejection and the tenant-isolation guarantee (two betriebe, each only ever sees its own reservations) end-to-end against a real running Express instance.
- There is currently no self-service signup: a betrieb's password is set via `setzeBetriebPasswort(slug, password)`, intended to be called from the agency dashboard (Section E) when a site goes live. Wiring that dashboard button is listed as a remaining gap in the final report — the function and its storage exist and are tested, the dashboard UI trigger for it is not yet built.
- Public, cross-origin routes (`/betrieb/:slug/konfiguration`, `/betrieb/:slug/reservierung`, `/betrieb/:slug/bestellung`) are what the static customer sites' `reservation-form`/`order-embed` blueprints call — `ctx.apiBase` is now threaded from `WIRT_API_BASE_URL` through `renderSite()`/`buildAll()` so built sites point at the actual portal origin instead of a relative path that would only work if both were on the same domain.
- No-show flow matches the brief: the order endpoint requires explicit `noShowZustimmung: true` whenever `noShowSchutzAktiv` is on, and the exact consent text + timestamp are generated server-side and stored on the order (never trusted from the client) — mirroring the v1 design's reasoning that the legal text and the enforced condition must never be able to drift apart. `bestaetigeNoShow` only allows the confirmed amount to be corrected downward, never above what the guest agreed to. `zuverlaessigkeitsWarnung()` surfaces a per-phone-number warning once the configurable threshold is hit, but nothing auto-blocks a guest — the brief is explicit that this is a warning signal, not an automatic block. `src/wirt/pdf.js` renders a Vorgangsquittung (protocol) PDF via the already-present `pdfkit` dependency, explicitly labelled as not an invoice or standalone legal demand.
- Web Push is the default channel (`src/wirt/push.js`, using the `web-push` package added this session), driven by `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`; without those env vars, `sendPushToBetrieb` is a documented no-op rather than throwing, so the portal keeps working with zero push configuration. Telegram (`src/wirt/telegram.js`) is the optional fallback: `sendTelegramMessage`/`notifyBetrieb` no-op without `TELEGRAM_BOT_TOKEN`, and `handleCommand` checks the incoming chat id against the betrieb's own stored `telegramChatId` before running `/bestätigen`, `/absagen`, `/bereit` or `/heute` — one betrieb's Telegram chat can never act on another's data. `startTelegramPolling` is a simple `getUpdates` long-poll loop (no separate public webhook endpoint needed); it is not started by default and not covered by an automated test, since that would require a live Telegram bot token and network access this session doesn't have reason to exercise.
- Frontend is a framework-free PWA: `src/wirt/public/{login,index}.html` + `app.js` (vanilla fetch/EventSource, CSRF token read from the non-HttpOnly cookie) + `manifest.json` + `service-worker.js` (push → `showNotification`). Live updates (new reservation/order, status changes) are pushed to open portal tabs over Server-Sent Events (`GET /api/events`), scoped per-slug via an in-memory `Map<slug, Set<res>>` that is never persisted and never shared across tenants.
- Not yet built in this session, called out explicitly rather than claimed done: a full visual design pass on the portal UI (it is functional/accessible — focus rings, labelled inputs, keyboard-operable buttons — but not art-directed the way customer sites are, since the brief's aesthetic requirement was for the dashboard, not this portal); and any live verification of the Telegram bot loop or Web Push delivery against a real browser/device, since both need external credentials this environment doesn't have.

## 2026-09-23 — Section E: Agency dashboard
- `dashboard/server.js` is framework-free on the client (no bundler, one vanilla `app.js` doing `pushState` client-side routing) and binds only to `127.0.0.1` by default (`HOST_DASHBOARD` env, already defaulted in `.env.example`). Server routes `/leads`, `/lead/:id`, `/lead/:id/edit`, `/lead/:id/build`, `/neu`, `/einstellungen` all serve the same `index.html` shell so deep links and reloads work; the client router then renders the right view from the URL.
- A "lead" is simply a `data/*.json` briefing file — the dashboard is a thin, honest view over the same `validateBriefing`/`compose` pipeline the build uses, not a separate data model. The lead detail view runs `compose()` live so the agency sees the actual archetype/section list/build-readiness before ever running a build.
- Every writing route (`POST /api/leads`, `PUT /api/leads/:id`, `POST /api/leads/:id/build`, `POST /api/einstellungen/wirt-passwort`) is gated by `dashboard/auth.js`'s `requireDashboardToken`, a constant-time `Bearer` comparison against `DASHBOARD_TOKEN`. Read routes are open, since the whole server is loopback-only by construction. The token itself is never written into any HTML the server sends and never logged; the browser-side counterpart stores it only in `localStorage` after the operator pastes it once on `/einstellungen`, and it round-trips only as an `Authorization` header, never echoed back by the server.
- `GET /api/einstellungen` reports configuration as booleans (`dashboardTokenConfigured`, `vapidConfigured`, `telegramConfigured`, ...), never the underlying secret values — `test/dashboard.test.js` asserts the actual `DASHBOARD_TOKEN`/`WIRT_SESSION_SECRET` strings never appear anywhere in that response.
- The edit form covers the scalar `{status,value}` fields (konzept, usp, signaturgericht, ambienteCharakter, telefon, adresse, ...) as paired value+status inputs, plus a JSON textarea for the structurally nested fields (fotos, speisekarte, testimonials, historie, oeffnungszeiten, freigabe, ...) rather than a bespoke dynamic-array editor for each — validated server-side through the same `validateBriefing` before anything is written, so a malformed edit can't corrupt a briefing file. This is a real time/scope trade-off, not a placeholder: it is fully functional end-to-end (create, edit, validate, build), just less polished than a dedicated field-by-field editor for arrays would be.
- `/einstellungen` also exposes `setzeBetriebPasswort` (Section F's wirt-portal auth) behind the same Bearer-token gate — this is the "go live" action that gives a betrieb its own wirt-portal login, closing the integration gap noted in the Section F entry above.
- `test/dashboard.test.js` runs the real Express app against a temporary copy of `data/` (restored after the test) and covers: write routes rejecting missing/wrong tokens, a full create→list→detail→edit round trip, invalid-briefing rejection with structured errors, and the settings endpoint never leaking secret values.

## 2026-09-23 — Section G: Migration and remaining tests
- `scripts/migrate-from-v1.js migrate({v1RepoPath})` reads only `<v1 repo>/v2/briefings/*.json` (see the earlier v1-data-source finding) and writes v3-shaped briefings to `data/migrated/<slug>.json` (now gitignored, like `docs/` and `data/runtime/`, since it's generated output the agency reviews and moves into `data/` deliberately, not source to commit as-is) plus a human-readable `data/migrated/MIGRATION_REPORT.md`. It never writes into the v1 checkout (verified by `test/migrate.test.js`) and never writes into `data/` directly.
- Per the brief, every migrated *optional* field is forced to `status: 'draft'` regardless of what status the v1 source claimed (`bestaetigt`/`uebernommen`/`vorschlag` all become `draft`) — migration proposes, it never self-confirms. Required plain fields (`name`, `kueche`, `ort`, `hauptaktion`) are taken as-is when present; `kueche` free text is keyword-matched onto the v3 enum (defaulting to `international` with a manual-review note on no match), and an invalid/missing `hauptaktion` defaults to `informieren` with the same kind of note.
- Two migration mappings were deliberately made *lossy* rather than fabricated, after inspecting the actual v1 pilot data (`v2/briefings/*.json`, all four explicitly marked `"fiktiv": true`):
  - `karte.speisekarte` in v1 is a reference to a shared template catalog (e.g. `{"katalog":"bayerisch"}`), never real dish/price data for that specific house — migrating it into v3's `speisekarte` array would fabricate a menu. It is left `draft`/`null` with a report note instead; only `signaturgericht` (a named dish, taking the first of any listed) is carried over.
  - `stil.referenzen` mixes real `https://` URLs with plain prose references (e.g. `"bargoto.com (Izakaya in New York)"`); only entries that already parse as a valid `https://` URL become `referenzUrls`, the rest are listed in the manual-review notes rather than guessed into a URL.
  - `marke.farben` holds free-text color names (e.g. `"Laternenrot"`), not hex codes; `primaerfarbe` needs a validated `#rrggbb` value, so it is left empty with a note rather than guessing a hex value for a named color.
  - `belege.googleBewertung` (a star rating) has no corresponding v3 field at all and is reported as unmigrated rather than silently dropped.
  - Migrated stock photos (`medien.fotos`, all marked `herkunft: 'stock'` in v1 — Unsplash placeholders, not the actual establishment) are carried over as draft `fotos` entries with `confirmed: false` on every photo, exactly preserving that they are not verified photos of the real place.
- Final verification (`npm ci` + `npm test` + `npm run build` in a clean environment, see final report) caught a real bug via the judge's own responsive-guard check: `gallery-mosaic`'s desktop grid was the CSS default with a `@media(max-width:767px)` mobile override, the opposite of every other asymmetric blueprint's mobile-first pattern, so it never matched the judge's `@media(min-width:768px)` check even though it was visually responsive. Fixed by rewriting it mobile-first like the rest (2-column base, 4-column `@media(min-width:768px)` override) rather than loosening the judge's check.
- Ran the migration against the real, publicly cloned `Seifinger/gastro-webagentur` checkout (`V1_REPO_PATH=<checkout> npm run migrate:v1`): all 4 pilot briefings migrated to schema-valid v3 output with a populated `MIGRATION_REPORT.md`; this was a real run against real v1 data, not a synthetic test fixture, though the source data itself is fictional pilot content.
- Remaining test coverage added to close out the brief's explicit list: `test/build-reservation.integration.test.js` builds a real site with `WIRT_API_BASE_URL` set, asserts the rendered `reservation-form`'s endpoint matches a live wirt-portal instance, POSTs to that exact endpoint, and confirms the reservation lands in that tenant's store — an end-to-end build+reservation-route integration test, not just two separate unit tests. Combined with `test/wirt.test.js` (auth + tenant isolation + CSRF) and the provenance assertions spread across `test/briefing.test.js`/`test/blueprints.test.js`/`test/migrate.test.js`, every category the brief names (validator, token contrast, five composer briefings, all blueprint exports, renderer metadata/HTML, positive/negative judge cases, build+reservation integration, auth/tenant-separation/provenance) has direct test coverage.

## 2026-09-23 — Prospect workflow repair (Windows test bug + broken /prospects UI)
- Context: two commits landed directly on `main` after the initial build (outside this session): `feat: add Google Places lead finder` (`dashboard/lead-finder-server.js`, route `/lead-finder`) and `feat: add scored prospect workflow and local demos` (`dashboard/prospect-server.js`, route `/prospects`). Both call the Google Places Text Search API independently for different purposes (lead-finder just vets/saves place IDs for manual briefing entry; prospect-server imports full candidates, scores their websites, and offers a local pitch demo). They don't share code and neither is broken by the other, so per "don't rebuild working modules unnecessarily" `lead-finder-server.js` was left untouched — only `prospect-server.js` and its frontend were repaired.
- **Windows migration test bug**: `test/migrate.test.js` built output paths with `new URL('../package.json', import.meta.url).pathname`. `URL.pathname` on a Windows `file://` URL keeps a leading `/` before the drive letter (`/C:/Users/...`); passing that into `path.join` with further Windows-style joins is what produced the doubled `C:\C:\...` prefix. Fixed by computing `rootDir` once via `path.dirname(fileURLToPath(new URL('../package.json', import.meta.url)))` — `fileURLToPath` is the platform-correct converter and is the same pattern already used in `test/dashboard.test.js`. Verified the fix doesn't change Linux behavior (all 4 migrate tests still pass) since this environment has no Windows to test on directly; the fix is the documented, standard-library-correct way to convert a `file://` URL to a filesystem path, not a guess.
- **Why the "Suchen" button did nothing**: the original `prospect-server.js` rendered the entire interactive page as one minified template-string function, with `onclick="an('` + id + `')"` attributes built by string concatenation around single-quoted place IDs — any place name or ID containing an apostrophe (not uncommon, e.g. "Da Vito's") would have broken the generated HTML's quoting, and more generally the whole page had zero separation between markup and behavior, making it fragile and unreviewable. Root-caused by reading the actual shipped code rather than assuming; the described "fragile inline JS" diagnosis in the task matched what was actually there.
- **Split**: `dashboard/prospect-server.js` now only holds Express routes, the Google Places call (`searchGooglePlaces`), heuristic analysis (`analyzeWebsite`), scoring (`scoreProspect`), and the (still template-string, but static/non-interactive) demo-preview HTML — no interactive JS in a template string. The interactive UI moved to `dashboard/public/prospect.html` + `dashboard/public/prospect.js`, the latter using only `addEventListener`/`textContent`/`createElement`, no inline handlers, no dynamically built JS strings. Small prospect-scoped CSS rules were added to the existing `dashboard/public/styles.css` (scoped under `#search-results`/`#prospect-list` IDs, not a redefinition of the shared `.lead-row` class used by the main Leads page) rather than a new stylesheet file, per the instruction to reuse and extend the existing one.
- **API reshaped to be RESTful** (was: everything as `POST /api/prospects/<verb>`, unshipped and not depended on by anything, so no compatibility cost): `GET /prospects` (page), `POST /api/prospects/search` (costs money, must stay POST), `GET /api/prospects` (list+scoring), `POST /api/prospects` (import), `POST /api/prospects/:placeId/analyze` (analyze). All five still gated by `requireDashboardToken`, reusing the existing constant-time Bearer check unchanged.
- **Dropped the separate `POST /api/prospects/:id/demo` "build demo" endpoint** from the original: `GET /prospect-preview/:placeId` already renders the concept demo live from the stored prospect record on every request, so a prior "generate" step did nothing but add a network round-trip and a false impression of persisted build state. `prospect.js`'s "Konzeptdemo öffnen" is a plain link to `/prospect-preview/:placeId` (`target="_blank"`).
- **Concurrency limit**: added a small in-process semaphore (`createLimiter`, cap 5) wrapping every `analyzeWebsite` call server-side, so even several simultaneous analyze requests (multiple tabs, fast repeated clicks) never run more than 5 outbound website fetches at once — enforced centrally rather than trusted to client-side button-disabling alone.
- **Scoring/analysis rules implemented exactly as specified** (kept the pre-existing formula, which already matched): no website → 100/"Sehr hoch – keine Website"; unreachable or unanalyzed website → `score: null`, "Zu prüfen", never a guessed number; reachable site accumulates +25 no order / +20 no reservation / +25 no mobile viewport / +20 copyright footer ≥3 years old / +10 no HTTPS, with priority bands ≥80 "Sehr hoch", ≥50 "Hoch", ≥25 "Mittel", else "Niedrig". `analyzeWebsite` does a single honest `GET` with an identifying User-Agent, an 8s timeout, and never attempts login/paywall/robots.txt bypass or headless-browser rendering.
- **No Google photos/review text**: `searchGooglePlaces`'s field mask only ever requests id/name/address/phone/website/rating-number/rating-count — no photo or review-text fields exist to leak. The demo preview only ever interpolates the prospect's `name` and the region parsed from `adresse`; phone, rating and review count are never written into the rendered HTML (covered by `test/prospect.test.js`).
- **Prospect storage**: `data/runtime/prospects.json`, already covered by the existing `data/runtime/` gitignore rule — no new ignore entry needed. Added a `setProspectStoreFile()` test seam (mirrors `src/wirt/store.js`'s `setRuntimeDir`) so tests never touch the real store file.
- **Tests mock `fetch` entirely** (`request` injection parameter on `searchGooglePlaces`/`analyzeWebsite`, same pattern as `dashboard/lead-finder-server.js`'s existing `searchPlaces`): no live Google Places calls or live website fetches happen in `npm test`.

## 2026-09-23 — Closing the three known limitations from the prospect-workflow fix
Follow-up to the previous entry, addressing each gap concretely rather than leaving it as a caveat:

- **"No native Windows verification"**: added `.github/workflows/test.yml`, a CI matrix running `npm ci && npm test && npm run build` on both `ubuntu-latest` and `windows-latest` for every push to `main` and every PR. This gives an actual, repeatable, automated Windows test run — not just an argument that the `fileURLToPath` fix "should" be platform-correct. Also added `test/windows-path-safety.test.js`, an OS-independent regression guard that scans the whole source tree for the exact broken pattern (`new URL(...).pathname` used for a filesystem path) so this bug class can't quietly reappear in a new file even between CI runs; verified it actually fails by temporarily reintroducing the pattern in a scratch file before removing it again.
- **"No live Google Places verification"**: a real live call requires a real `GOOGLE_PLACES_API_KEY`, which this session has no access to and should not ask the user to paste into chat — that constraint doesn't go away by re-implementing anything. What was done instead: (1) hardened `searchGooglePlaces` against the documented real-world response variations of the Places API (New) `searchText` endpoint — a non-JSON error body from an intermediate proxy/gateway no longer produces a raw `SyntaxError`, Google's own `error.message` is now surfaced alongside the HTTP status for any non-403/429 failure, a 200 response with no `places` key is treated as zero results rather than risking a crash, and places entries missing `id`/`displayName`/`rating`/etc. (which real search results routinely have, depending on place type) are handled the same way they were already designed to be, now with tests proving it; (2) added `scripts/check-google-places-live.js` (`npm run check:google-places -- "<query>"`), a manual, opt-in script — explicitly outside `npm test` — that the user can run once locally with their own key to see the real, parsed response and any fields it reports as missing. This session verified the script's no-key error path (the one part testable without credentials); the actual live-success path can only be confirmed by whoever holds the key.

No code change closes this "gap" because closing it would mean claiming certainty the analysis doesn't have; the UI already states this explicitly (`dashboard/public/prospect.html`'s hint text) and `DECISIONS.md`'s previous entry documents the exact scoring rules so the heuristic is at least transparent and reproducible.

## 2026-09-23 — Real Windows CI caught a genuine test-isolation race (not a Windows-only bug)
The new `windows-latest` CI job (added in the previous entry) failed on its very first run — this is exactly why it was added instead of just arguing the fix was correct. Root cause, from the actual job log:

```
not ok 30 - test/dashboard.test.js
  failureType: 'hookFailed'
  error: "ENOTEMPTY: directory not empty, rmdir 'D:\a\gastro-v3\gastro-v3\data'"
```

`test/dashboard.test.js` read/wrote the **real** `data/` directory directly (backing it up and restoring it around the test, per its own old comment: "the dashboard server module reads from the real data/ directory... so this test writes into data/ directly"). Node's test runner runs test files concurrently by default, and `test/migrate.test.js` independently writes into `data/migrated/` and cleans it up. The two collided: `dashboard.test.js`'s `test.after` hook tried to `rm(dataDir, {recursive:true})` while `migrate.test.js` was concurrently creating/removing files inside `data/migrated/` in another process. POSIX directory deletion tolerates that kind of race far more gracefully than Windows NTFS does, which is why it only surfaced here — but the underlying bug (two test files mutating the same real, shared directory with no coordination) was there on every OS, including the one this was developed on.

Fix: `dashboard/server.js`'s `createDashboardApp()` now takes optional `{ dataDir, docsDir }` (mirroring the same pattern `scripts/build.js`'s `buildAll()` and `src/wirt/store.js`'s `setRuntimeDir()` already use), defaulting to the real repo directories for actual `npm run dev` usage. `test/dashboard.test.js` now creates its own temp `dataDir`/`docsDir` via `mkdtemp` and passes them in — it never touches the real `data/` directory at all anymore, which removes the backup/restore dance entirely (simpler, and the race is now structurally impossible rather than just timing-dependent). Verified locally: `npm test` passes repeatedly (3 consecutive runs) with the real `data/` directory left completely untouched (`git status` shows nothing there), and pushed to re-run the real Windows CI job to confirm.
